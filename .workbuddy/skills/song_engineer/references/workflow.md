# 标准工作流程与合并规则

song_engineer 三种模式的详细流程、合并规则与冲突处理。

---

## 模式 1：初始化模式流程

### Step 1：确定工程目标
- 确认歌名
- 确认/创建工程目录 `workspace/project/{歌名}/`
- 如已有 `project.md`，标记为"升级合并"模式（保留人工内容）

### Step 2：扫描散件产物
按以下路径模板查找（存在则读取）：

```
workspace/ai_chords/{歌名}/*.md              -> 和弦方案（可能有多个版本）
workspace/muse_ai/{歌名}/lyrics/lyrics.md    -> 歌词
workspace/muse_ai/{歌名}/lyrics/lyrics.design.md -> 歌词设计
workspace/muse_ai/{歌名}/lyrics.md           -> 歌词（备用位置）
workspace/audio_output/{歌名}/report.md      -> 音频分析报告
workspace/minimax_music_v3/{歌名}/            -> minimax 产物
workspace/project/{歌名}/project.md          -> 已有雏形（升级用）
```

### Step 3：提取与映射
按字段对照表（见工程MD格式规范第四节）将各产物信息提取到内存结构。

### Step 4：去重与冲突处理
同一字段多来源时的处理：

| 字段 | 优先来源 | 冲突时 |
|------|---------|--------|
| BPM | ai_chords > project雏形 > lyrics | 取优先来源值，其余记入日志"曾发现不一致" |
| 调号/Capo/编配调/实际音高 | ai_chords | 同上 |
| 和弦骨架 | ai_chords | 多版本时取最新（文件名带 _v2 优先于 _v1） |
| 歌词 | muse-lyrics-gen 的 lyrics.md | 如有 design.md，全局设定取 design |
| 段落结构 | ai_chords > project雏形 | - |
| 旋律特征 | audio report | 如无 report，从 ai_chords 的旋律构思提取 |

### Step 5：组装工程MD
按规范模板顺序组装各区块。缺失的区块写占位说明（如"待补充：多轨道规划"），不省略区块标题。

### Step 6：写工程日志
追加初始化记录：
```
| {日期} | 初始化 | 聚合自 ai_chords/lyrics/audio_report | song_engineer |
```

### Step 7：输出缺失清单
列出仍缺失的字段/区块，提示用户后续可补充的方向。

## 模式 2：诊断模式流程

### Step 1：读取工程MD
读取 `workspace/project/{歌名}/project.md`，解析为内存结构。
若文件不存在 -> 提示先跑初始化模式。

### Step 2：按五维诊断
依次执行 diagnosis_dimensions.md 的五个维度。每维产出结论。

### Step 3：生成诊断报告
按规范格式组装「现状诊断」+「优化建议」+「知识点」。

### Step 4：写入工程MD
**覆盖**「诊断与优化方向」整个区块（旧诊断进工程日志）。

### Step 5：追加工程日志
```
| {日期} | 诊断 | {完整性评分} {关键问题数} | song_engineer |
```

### Step 6：输出摘要
向用户输出诊断摘要 + 最优先的 1-3 条优化建议。

---

## 模式 3：优化模式流程

### Step 1：确认方向
解析用户意图，确定优化方向（和弦/歌词/结构/轨道/旋律/扒谱）。
如未指定方向 -> 先跑诊断，取最高优先级建议的方向。

### Step 2：前置诊断（可选）
如工程MD 的诊断区块为空或超过 24 小时未诊断，先跑诊断模式。

### Step 3：调用生成技能
根据方向调用对应技能（见 SKILL.md 协作图），传入工程MD 相关区块作为输入。

### Step 4：合并产出
将生成技能的新产出按合并规则写回工程MD。

### Step 5：追加工程日志
```
| {日期} | 优化 | {方向}：{变更摘要} | song_engineer + {生成技能名} |
```

### Step 6：输出变更摘要
告知用户改了什么、为什么改、可如何回退（Git）。

## 合并规则

### 规则 1：核心信息内嵌，大文件引用
- 和弦骨架/段落结构/歌词正文/多轨规划/诊断 -> 内嵌
- wav/mid/mp3/report.md/编曲方案.md -> 相对路径引用

### 规则 2：人工编辑保护
工程日志中标记为 `人工编辑` 的内容，合并时不自动覆盖。如确认需覆盖：
1. 追加日志记录"覆盖人工编辑：{原内容摘要}"
2. 执行覆盖
3. 提示用户

### 规则 3：字段级更新
优化某方向时，只更新对应区块，不动其他区块。如"优化和弦"只动「和弦详情」，不改「歌词」。

### 规则 4：日志只追加
工程日志和工程MD本身的历史版本（Git管理）负责回溯，日志行只追加不修改不删除。

### 规则 5：诊断区块可覆盖
「诊断与优化方向」是最新状态的快照，每次诊断覆盖。旧诊断的关键结论应先沉淀进工程日志。

## 冲突处理

### 场景 A：用户手动改了工程MD，与引用产物不一致
- 信任工程MD（最新人工意图）
- 诊断时标 ⚠️ 提示"工程MD 与 {产物} 不一致，以工程MD为准"
- 不自动同步回产物

### 场景 B：两个产物对同一字段给出不同值
- 按字段优先来源表取值
- 日志记录冲突
- 诊断时提示用户确认

### 场景 C：生成技能产出与现有工程MD冲突
- 生成技能产出是新意图，优先
- 保留被替换内容的日志记录
- 提示用户可 Git 回退

## 路径基准

所有相对路径以工程文件所在目录 `workspace/project/{歌名}/` 为基准。

常见引用路径（从工程MD看）：
```
../../ai_chords/{歌名}/                    和弦方案
../../muse_ai/{歌名}/lyrics/lyrics.md      歌词
../../audio_output/{歌名}/                  音频分析
../../audio_output/{歌名}/report.md        分析报告
attachments/hum.wav                         附件（同目录）
```
